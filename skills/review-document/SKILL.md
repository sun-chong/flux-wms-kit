# 多视角文档评审技能

## 概述

当用户通过 `/review-document @path1 @path2 ...` 调用时，本技能将：
1. 验证指定的文档路径存在（不读取内容）
2. 用 Grep 轻量检测文档是否涉及 PL/SQL 代码
3. 并行启动多个 subagent，各自独立读取文件并从不同角度评审
4. 交叉验证门控通过后，汇总所有结果，按严重程度输出结构化报告

## 铁律（必须遵守）

**本技能是纯评审操作，严禁修改任何代码或文件。**

```
╔═════════════════════════════════════════════════════╗
║  绝对禁止：                                          ║
║  1. 修改任何文件（包括 .sql、.md、配置文件等）         ║
║  2. 创建新文件                                       ║
║  3. 直接实现文档中的代码或逻辑                        ║
║  4. 写任何 SQL、命令或脚本（除了评审报告本身）         ║
║                                                     ║
║  本技能的输出只有一样东西：评审报告                    ║
╚═════════════════════════════════════════════════════╝
```

违反此规则的后果：**评审结果作废，重新执行**。此规则适用于主 Agent 和所有 subagent。

## 评审原则

参考 `receiving-code-review` 模式，评审本身必须保持技术客观：

- **评审是技术评估，不是情绪化表达** — 每个发现都要有技术依据
- **不做过场式肯定** — 不使用"很好的设计"、"没有问题"等空泛表述
- **需求可以质疑** — 如果需求不合理、不完整或存在矛盾，明确指出
- **验证后再下结论** — 对照代码库现实、项目规范、历史经验进行验证

## 评审视角

### 始终启动的基础视角（2 个）

| 视角 | 职责 | 检查要点 |
|------|------|---------|
| **需求合理性审查** | 分析需求是否合理、完整、一致 | 见 `references/review-dimensions.md#需求合理性审查` |
| **设计完整性审查** | 审查计划/设计的可执行性 | 见 `references/review-dimensions.md#设计完整性审查` |

### 条件启动的 PLSQL 视角（文档含 PL/SQL 代码时追加 2 个）

| 视角 | 职责 | 检查要点 |
|------|------|---------|
| **PLSQL规范审查** | 按 `plsql.md` + `ddl-template` 规范审查代码 | 见 `references/review-dimensions.md#PLSQL规范审查` |
| **Oracle代码审查** | 调用 `oracle-reviewer` agent 进行专业审查 | 见 `references/review-dimensions.md#Oracle代码审查` |

## 进度跟踪（强制）

你 **必须** 在开始工作前为以下每个步骤创建 Task，并在完成每个步骤后更新状态：

1. **输入解析与存在性验证** — 提取 @path，Glob 验证文件存在
2. **PL/SQL 特征检测** — Grep 检测是否含 PL/SQL
3. **分发 Subagent** — 并行启动 2-4 个评审 subagent
4. **门控验证与汇总** — 提取 VERIFICATION 头部，主 Agent 交叉验证标识符，按严重程度分类汇总
5. **输出评审报告** — 按模板输出最终报告

**禁止跳过任何步骤。Subagent 返回的是中间数据，不是最终输出。**

## 工作流程

### Step 1: 解析输入与存在性验证

从用户消息中提取所有 `@path` 格式的文档路径。支持：
- 绝对路径：`@C:\path\to\doc.md`
- 相对路径（相对项目根目录）：`@docs\superpowers\specs\xxx.md`
- 多个文档同时指定：`/review-document @spec.md @plan.md`

**【重要】再次评审的处理**：
- 如果用户说"再次评审"、"重新评审"、"再评审一次"或类似表达（且没有提供新的 `@path`），则**自动使用上一次评审的文档路径**
- 原因：用户说"再次评审"意味着原文档已更新，需要全新审查，而不是询问是否评审其他文档
- 如果用户提供了新的 `@path`，则使用新路径（覆盖上一次的记忆）

对每个路径执行存在性检查（Glob），路径不存在则提示用户。

**【禁止】本步骤不读取文件内容。** 文件内容由 subagent 独立读取（见 Step 3）。

### Step 2: PL/SQL 特征检测（轻量）

用 Grep 在目标文件中搜索以下关键词（任一命中即判定为含 PL/SQL）：
- `CREATE OR REPLACE`
- `SPUDF_` 或 `PLS_` 或 `FNUDF_`
- `SELECT.*INTO`

命中 → 启动 4 个视角（基础 2 + PLSQL 2）；未命中 → 仅启动 2 个基础视角。

本步骤仅用于判断启动哪些视角，不读取文件全文。

### Step 3: 分发 Subagent

并行启动以下 subagent（基础 2 个，含 PLSQL 则加 2 个）：

| 视角 | 职责 | 检查要点 |
|------|------|---------|
| **需求合理性审查** | 分析需求是否合理、完整、一致 | 见 `references/review-dimensions.md#需求合理性审查` |
| **设计完整性审查** | 审查计划/设计的可执行性 | 见 `references/review-dimensions.md#设计完整性审查` |
| **PLSQL规范审查**（条件） | 按 `plsql.md` + `ddl-template` 规范审查代码 | 见 `references/review-dimensions.md#PLSQL规范审查` |
| **Oracle代码审查**（条件） | 调用 `oracle-reviewer` agent 进行专业审查 | 见 `references/review-dimensions.md#Oracle代码审查` |

每个 subagent 的 prompt 必须包含：
- **文件绝对路径**（不是文件内容）
- 该视角的检查清单（从 `references/review-dimensions.md` 对应节读入）
- 项目规范文件内容（如 plsql.md、ddl-template）
- **铁律**和**文件读取要求**及**返回格式要求**（见下方模板）

**重要**：所有 subagent 必须并行启动（在同一个消息中发起多个 Agent 调用），不串行。

> **【关键】Subagent 全部返回后，你必须继续执行后续步骤，禁止在此处停止：**
>
> ```
> 收到 subagent 返回 → 标记 Task 3 完成 → 执行 Step 4: 门控验证与汇总
> → 标记 Task 4 完成 → 执行 Step 5: 输出报告
> ```
>
> Subagent 的评审输出是 **待处理的中间数据**，不是最终报告。
> 你的任务还没有完成——后续的门控验证和汇总输出才是本 Skill 的交付物。

#### Subagent Prompt 模板

每个 subagent 的 prompt 应包含以下结构：

````
# 角色：{视角名称}审查员

## 铁律
**纯评审操作，禁止修改任何文件、创建任何文件、实现任何代码。只能输出观察和评估。**

## 文件读取要求（必须遵守）

你必须**自行读取**以下文件获取评审内容，禁止依赖任何预置的文件内容：
- 文件路径：{absolute_path}

**读取后验证**：读取文件后，用 Grep 在该文件中搜索至少 2 个你从文档中识别的关键标识符
（如存储过程名、表名、变量名），确认它们确实存在于文件中。如果验证失败，立即终止评审
并在返回中说明。

## 检查清单
{从 review-dimensions.md 对应节复制}

## 返回格式要求（必须遵守）

你的返回必须**以以下结构化头部开始**，中间不能插入其他内容：

---VERIFICATION---
FILE: {你实际读取的文件绝对路径}
TITLE: {文档标题，取文件中第一个 # 标题}
KEY_IDENTIFIERS: {逗号分隔的关键标识符列表，如存储过程名、表名，至少 3 个}
VERIFIED: YES 或 NO（Grep 验证是否全部通过）
---END VERIFICATION---

[空一行后，接你的评审内容]

评审内容格式要求：
{检查清单的输出格式要求}
````

### Step 4: 门控验证与汇总

> **⚠️ 本步骤是评审报告的前置条件，未完成门控验证禁止输出报告。**

#### 4.1 门控验证

在汇总评审结果之前，执行交叉验证门控：

1. **提取验证头部**：从每个 subagent 返回中解析 `---VERIFICATION---` 至 `---END VERIFICATION---` 之间的字段
2. **检查 VERIFIED 字段**：任一 subagent 报告 `VERIFIED: NO` → 阻断
3. **主 Agent 交叉验证**：
   - 从所有 subagent 的 KEY_IDENTIFIERS 中提取并集（去重）
   - 用 Grep 在目标文件中验证这些标识符是否存在（可合并为一次 Grep，用 `|` 连接）
4. **判定**：
   - ✅ 全部标识符存在于文件中 → 门控通过，进入 4.2 汇总
   - ❌ 任一标识符不存在 → 阻断，不输出评审报告，向用户报告：

     > ⚠️ **评审门控阻断**
     > Subagent 声称读到的关键标识符在文件中不存在，可能存在内容幻读：
     > - 不存在的标识符：{列表}
     > - 来源 subagent：{name}
     > 评审报告已中止，请检查文件内容后重新评审。

#### 4.2 汇总结果

门控通过后，收集所有 subagent 的评审输出（忽略 `---VERIFICATION---` 头部），按严重程度分类：

| 级别 | 含义 | 示例 |
|------|------|------|
| **阻断** | 导致编译失败或完全不可用 | Oracle 11g 不兼容语法、缺少必要参数 |
| **严重** | 导致功能错误或数据问题 | 空值判断错误、异常未处理、逻辑缺失 |
| **重要** | 影响可维护性、性能或一致性 | 命名不规范、缺少注释 |
| **一般** | 建议性的改进 | 可选的优化、格式调整 |

### Step 5: 输出报告

使用 `references/report-template.md` 中的模板输出最终报告。

同一问题只出现一次（多个视角发现相同问题时不重复）。

## 关键行为约束

0. **【铁律】纯评审，不修改** — 这是最重要的一条：评审过程中禁止写任何文件、创建任何文件、实现任何代码。违反此规则会导致评审作废。
1. **【防提前完成】Subagent 返回后禁止停止** — 并行 subagent 全部返回后，必须继续执行门控验证和汇总报告。Subagent 输出 ≠ 最终报告。如果在此处停止，评审任务实质上只完成了一半
2. **主 Agent 禁止读取评审目标文件的全文内容** — 只做 Grep 特征检测（Step 2），不 Read 文件
3. **subagent 自主读取 + 自主验证** — 每个 subagent 独立 Read 文件，读完后用 Grep 验证关键标识符
4. **门控阻断** — 主 Agent 汇总前必须通过交叉验证门控（Step 4.1），任一标识符不存在即阻断
5. **并行启动所有 subagent** — 不串行等待结果；一次性启动所有 subagent
6. **不要对结果做二次修改** — subagent 的评审结果应如实汇总，不添加主 Agent 自己的判断（除非是汇总级别的去重和排序）
7. **如果一个视角没有发现问题，该视角不出现在报告中** — 避免"未发现问题"这种空泛表述
8. **历史经验调用** — 在 subagent prompt 中引导其查阅 project memory 中的历史记录，但不用单独开一个 subagent
