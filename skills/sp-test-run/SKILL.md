# Oracle 存储过程测试 Skill (sp-test)

## 核心测试方法论

### 基本原则

**在找出根本原因之前，不要贸然做出错误假设**——过早下结论会延长解决问题的时间。正确的做法是在探索根本原因的同时，尽可能收集更多的诊断数据，这些数据既能用于结果验证，也能用于问题修复。

### 测试循环

每个测试遵循一个完整的数据驱动闭环：

```
建立基准 → 执行操作 → 收集数据 → 对比分析 → 验证假设 → 记录结论
```

1. **建立基准**：在执行任何操作之前，先查询当前业务状态。基线数据是判断测试是否产生预期影响的唯一可靠参照。

2. **执行操作**：用特定参数调用目标存储过程，记录完整的返回信息，包括返回码、输出参数和DBMS_OUTPUT。

3. **收集诊断数据**：执行后立即查询相关表，收集完整的状态快照。这一步不是为了验证某个假设，而是尽可能全面地采集数据，为后续分析提供充足的素材。

4. **对比分析**：将执行后的状态与基线进行逐项对比，识别数据变化。变化可能是预期的（任务创建、库存更新），也可能是意外的（不该修改的数据被修改了）。

5. **验证假设**：如果发现异常，用最小可复现查询逐一验证可能的根因。每次只改变一个变量，避免多个假设同时验证导致结论混淆。

6. **记录结论**：将测试的全部过程、数据和结论记录下来。完整的记录不仅服务于本次测试，也为后续的回归测试和问题排查提供参考。

### 测试的组织方式

每次测试针对一个存储过程的一组参数组合。每个参数组合构成一个独立的测试用例，包含：入参、预期行为、数据采集范围。测试用例之间通过数据库状态产生关联——前一个用例创建的数据可能影响后一个用例的计算逻辑，因此测试用例必须按顺序执行。

### 数据驱动的异常分析

当测试结果与预期不符时：

1. 不要急于猜测根因，先检查已收集的诊断数据是否足以定位问题
2. 如果数据不足，补充查询相关表，扩大数据采集范围
3. 用最小可复现查询逐一验证每个可能的根因
4. 每次验证后更新假设，而不是固守最初的判断
5. 将定位到的根因记录到测试报告中

这种方法避免了在错误的方向上浪费时间，也确保了问题修复后有足够的数据验证修复效果。

### Subagent 调度策略

由于测试用例之间存在数据库状态依赖（前一个用例COMMIT后的数据会影响后续用例），每个测试用例由独立的 Subagent 执行，并且必须按顺序串行调度：前一个 Subagent 完成全部操作并 COMMIT 后，才能启动下一个。</｜DSML｜parameter>

## 完整工作流

### Phase 0：环境确认（主 Agent）

```
用户提出测试请求 → 检查是否已连接数据库 → 确认测试环境（组织、仓库）
```

1. 确认数据库连接配置（从项目根目录 `.env` 获取 `DB_CONNECTION`）
2. 确认测试的组织 ID 和仓库 ID
3. 通过 `connect-oracle` 连接数据库

---

### Phase 1：源码分析与自动基线（主 Agent）

读取存储过程源码，自动分析其依赖的表结构，生成基线查询。

**步骤：**

1. **读取源码**：从项目目录下的存储过程文件读取源码（如 `src/[模块]/routine/[存储过程名].sql`）
2. **提取表引用**：从源码中提取所有引用的表名：
   - `FROM` / `JOIN` 子句中的表
   - `UPDATE`、`INSERT INTO`、`DELETE FROM`、`MERGE INTO`、`INTO` 后的表
   - 注意过滤掉：CTE（WITH 子句）、子查询别名、Oracle 系统表
3. **自动生成基线查询**：对每个发现的表生成：
   ```sql
   -- 基础行数
   SELECT COUNT(*) AS CNT FROM [TABLE] WHERE 组织/仓库条件;
   
   -- 关键列分布（按状态、类型等维度分组）
   SELECT [STATUS_COLUMN], COUNT(*) AS CNT FROM [TABLE] GROUP BY [STATUS_COLUMN];
   ```
   基线查询应覆盖以下维度：
   - **基础行数**：每个依赖表的记录总量
   - **状态分布**：按状态字段分组统计（如 `STATUS`、`ACTIVEFLAG`）
   - **关键分布**：按业务维度分组统计（如区域、类型、分类）
   - **测试数据详情**：查询用户指定的测试数据（如托盘、单据、客户）的完整字段信息

4. **补充业务环境查询**：根据存储过程的业务领域，查询相关的环境配置表。这些表通常可以从源码中的规则配置、基础数据类表引用中识别。例如：
   - 规则配置表（`RUL_%` 类表）
   - 基础数据表（`BAS_%` 类表）
   - 库存表（`INV_%` 类表）
   - 任务/单据表（`DOC_%`、`ACT_%` 类表）

5. **执行基线查询**：通过 `connect-oracle` 执行所有基线查询

6. **结构化基线输出**：基线数据写入 `outputs/[SP名]_BASELINE_[日期].md`，采用结构化格式：
   - 测试数据清单（完整字段列表）
   - 环境配置摘要（规则、基础数据的关键配置）
   - 关键资源的交叉分布统计（如按两个维度分组的分布表）
   - 依赖表的基线快照（行数、关键列统计）

**与用户交互：**
- 展示发现的表列表和生成的基线查询
- 展示基线查询的执行结果摘要
- 让用户确认或补充需要查询的数据

### Phase 2：测试用例组织（主 Agent）

用户提供测试用例，来源可以是对话输入或 `sp-test-data-gen` 生成的测试方案文件。

**路径 A：从 `sp-test-data-gen` 测试方案文件读取（用户指定文件时）**

当用户提供 `sp-test-data-gen` 生成的测试方案文件路径时（如 `outputs/SPUDF_SWL_4FPICK_PROCESS_20260521_TEST_PLAN.md`），执行：

1. **读取文件** — 使用 Read 工具读取指定文件
2. **解析测试用例** — 从文件的「4. 详细测试用例」章节提取每个用例：
   - 用例ID（`HP-01` / `EP-01`）
   - 入参清单（`IN_PARAM1 => 'value'` 格式）
   - 预期结果（`OUT_CODE`）
   - 覆盖验证点
   - 验证 SQL
   - 前置条件
3. **转换为内部格式** — 为每个用例生成 `test_case[N]` 结构，包含：
   - 存储过程调用语句（完整 DECLARE 块，参数值从测试方案中提取）
   - 预期返回码
   - 验证 SQL（从测试方案中提取）
   - 输出文件路径
4. 与用户确认测试方案

**路径 B：用户在对话中提供（默认路径）**

用户以自然语言或 Markdown 表格提供参数组合：

```markdown
| 用例ID | 测试场景 | 参数组合 | 预期结果 | 验证点 |
|--------|---------|---------|---------|-------|
| TC-01 | [场景描述] | PARAM_A=val1, PARAM_B=val2 | [预期行为或返回码] | [验证维度] |
```

**主 Agent 处理（路径 B）：**
1. 将每个用例转为 `test_case[N]` 结构
2. 为每个用例准备：
   - 存储过程调用语句（完整 DECLARE 块）
   - 预期返回码
   - 预期输出特征
   - 副作用验证SQL
   - 输出文件路径
3. 与用户确认测试方案

### Phase 3：顺序 Subagent 执行（Subagent 串行）

**核心规则：**

- **必须顺序执行**，不能并行（因为每个测试会 COMMIT 修改数据库状态，影响后续测试的均衡计算）
- 每个参数组合 = 一个 Subagent = 一个独立的测试用例
- 前一个 Subagent 全部完成后（包括 COMMIT），才能启动下一个

**Subagent 初始化：**

每个 Subagent 接收到以下信息：
```
- 存储过程名: [SP_NAME]
- 参数组合: [PARAM_NAME]=[VALUE], ...
- 测试用例ID: [CASE_ID]
- 数据库连接: (来自项目根目录 .env)
- 组织/仓库: [ORG] / [WH]
- 基准数据快照: (Phase 1 的结果)
- 输出路径: outputs/[SP_NAME]_TEST_[CASE_ID]_[日期].md
```

**Subagent 必须执行的操作（5步协议）：**

```
[步骤 1] 前状态快照
- 查询当前业务数据状态（与测试相关的表）
- 记录到临时变量

[步骤 2] 执行存储过程
- 构造完整的 DECLARE...BEGIN...END 块
- 通过 connect-oracle 调用存储过程
- 捕获返回码、输出参数、DBMS_OUTPUT

[步骤 3] 结果校验
- 验证返回码是否符合预期
- 验证输出参数（如目标库位、任务ID）是否合理
- 对比预期结果

[步骤 4] 副作用检查
- 再次查询相关表，与步骤1的前状态对比
- 检查是否产生了预期外的数据变更
- 关键检查：库存变化、任务生成、状态更新

[步骤 5] 记录 + COMMIT
- 将测试结果写入独立的 Markdown 文件（outputs/[路径]）
- 格式见下方 "测试结果文件格式"
- 执行 COMMIT 提交事务
- 返回测试结果摘要给主 Agent
```

### 执行约束

1. **串行约束**：前一个 Subagent 必须完整执行完 Step 5（包括 COMMIT）后才能启动下一个
2. **COMMIT 规则**：每个 Subagent 必须在最后执行 COMMIT（除非测试验证回滚场景）
3. **连接方式**：所有数据库操作必须通过 `connect-oracle` skill（Bash + SQLcl 语法）
4. **独立文件**：每个 Subagent 必须将测试数据写入独立的 Markdown 文件
5. **错误处理**：如果存储过程执行出错，记录完整错误信息，仍然写入文件 + COMMIT

## 重要注意事项

1. **源码解析**：从存储过程源码提取表引用时，注意过滤：
   - WITH 子句的 CTE 名
   - 子查询别名
   - 系统表（`ALL_%`、`USER_%`、`DBA_%`、`V$%`）
   - 临时变量

2. **与用户交互**：
   - 展示自动发现的表和生成的基线查询，让用户确认
   - 展示完整的测试方案，让用户确认

3. **错误恢复**：
   - 如果某个 Subagent 失败，记录错误后继续下一个（不影响整体进度）
   - 在汇总报告中标记失败项及原因

4. **测试数据清理**：
   - 测试产生的数据在测试报告中记录
   - 如需清理，在最终报告中说明需要清理的数据
