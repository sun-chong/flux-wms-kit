# Oracle PL/SQL 存储过程测试数据生成

## ⚠️ 绝对禁令

### 禁令 1：严禁修改数据库
**这是最高优先级规则**。本 skill 全程只能执行 SELECT 查询。**一旦执行 INSERT、UPDATE、DELETE、CREATE、ALTER、DROP 或任何修改数据库的操作，就判定任务失败。** 没有例外。

### 禁令 2：严禁编造正确样本的数据
**成功路径（Happy Path）测试用例的所有入参值必须来自数据库真实查询结果**。唯一允许编造数据的情况是：故意制造错误样本（Error Path）来触发验证点。即使是错误样本，也应尽量基于真实数据做少量修改，而非凭空构造。

---

## 核心原则

1. **代码先行** — 先完整理解代码逻辑（包括所有子过程），再生成测试数据。不猜测、不假设。
2. **完整追踪** — 递归追踪所有调用链，不遗漏任何子过程。不知道的代码路径就是未测试的路径。
3. **双路径覆盖** — 同时考虑成功路径（Happy Path）和错误路径（Error Path）。只测成功不测错误，等于没测。
4. **数据真实** — 成功路径的参数必须来自数据库真实查询，**绝对禁止编造**。虚假的测试数据比没有测试数据更危险。
5. **只读底线** — 全程只执行 SELECT。任何 INSERT/UPDATE/DELETE/CREATE/ALTER/DROP 都是任务失败。
6. **客观覆盖** — 每个 IF 分支、每个 RAISE / RETURN 点都必须有对应的测试用例。

## 工作流概述

```
┌─────────────────────────────────────────────────────┐
│ Step 1: 读取并解析存储过程源码                        │
│   → 参数签名、局部变量、调用的子过程/函数             │
├─────────────────────────────────────────────────────┤
│ Step 2: 递归追踪完整依赖链                            │
│   → 构建调用树，直到叶子节点                          │
├─────────────────────────────────────────────────────┤
│ Step 3: 深度分析 SQL 逻辑与验证点                     │
│   → WHERE 条件、IF 分支、RAISE/ RETURN 点            │
├─────────────────────────────────────────────────────┤
│ Step 4: 连接数据库查询真实数据                        │
│   → 为每个逻辑路径找到匹配的数据                      │
├─────────────────────────────────────────────────────┤
│ Step 5: 生成结构化测试方案                            │
│   → 入参清单 + 预期结果 + 验证SQL + 测试步骤          │
└─────────────────────────────────────────────────────┘
```

## Step 1：读取并解析存储过程源码

### 1.1 读取主过程文件

使用 Read 工具读取目标存储过程的 `.sql` 文件。

### 1.2 解析过程签名

识别以下信息并记录：

- **过程名称** — 完整的 schema 限定名
- **输入参数** — `IN` 参数名称、数据类型（VARCHAR2, NUMBER, DATE 等）
- **输出参数** — `OUT` 参数，特别是 `OUT_CODE` 或类似的状态返回参数
- **参数默认值** — 记录所有有默认值的参数

### 1.3 识别调用依赖

扫描代码中的调用模式：

- `SPUDF_*` / `SP_*` / `FNUDF_*` — 自定义过程/函数调用
- `PLS_*` — 子系统过程调用
- 包中的函数调用（如 `pkg_name.func_name`）

列出所有被调用的子过程和函数，进入 Step 2 递归分析。

### 1.4 识别关键表引用

记录过程中引用的所有表名，特别是：

- 查询的驱动表（FROM 子句的第一个表）
- 条件过滤表（WHERE 子句中的字段所属表）
- 关联查询的依赖表

---

## Step 2：递归追踪完整依赖链

### 2.1 构建调用树

对 Step 1.3 中识别的每个子过程，重复 Step 1 的分析。构建一个完整的调用树，例如：

```
SPUDF_SWL_4FPICK_PROCESS          ← 主过程（根）
├── SPUDF_BARCODE_ANALYSIS        ← 1 层依赖
│   └── SPUDF_SPLIT_BARCODE       ← 2 层依赖
└── PLS_SNCHECKSCAN_PROCESS       ← 1 层依赖
    └── ...（更深依赖）
```

### 2.2 记录参数传递关系

对每个调用点，记录：

- 父过程传递了哪些参数值到子过程
- 参数是否经过了转换（如 NVL 处理、字符串拼接）
- 是否有硬编码的常量值传入（这是重要线索）

例如：
```
SPUDF_SWL_4FPICK_PROCESS
  → PLS_SNCHECKSCAN_PROCESS(
      IN_PICKINGZONE => 'SWL-4F',           ← 硬编码常量
      IN_BINDBOXNO   => '',                  ← 固定空值
      IN_USERID      => V_USERID             ← 变量传递
    )
```

### 2.3 终止条件

当以下情况时停止追踪该分支：

- 调用的系统包/函数（如 DBMS_OUTPUT、DBMS_UTILITY）
- 调用的标准 FLUX API（如 SP_* 标准过程），记录其已知行为即可
- 引用的函数已在项目外部或不可访问

---

## Step 3：深度分析 SQL 逻辑与验证点

这是最关键的一步，需要对每段 SQL 和每个分支条件进行系统化分析。

### 3.1 分类 SQL 语句类型

在代码中查找并分类每条 SQL：

| 类型 | 重点关注 |
|------|---------|
| SELECT INTO | 单行查询，注意 NO_DATA_FOUND / TOO_MANY_ROWS |
| 游标 FOR 循环 | 批量数据处理，注意每行内的条件分支 |
| INSERT | 写入哪些表、字段、数据来源 |
| UPDATE | 更新条件、更新的字段、影响的数据范围 |
| DELETE | 删除条件（通常在临时表上） |
| MERGE | 合并条件，匹配和不匹配时的操作 |

### 3.2 提取驱动查询条件

对每个查询，提取以下信息：

- **过滤条件** — WHERE 子句中的所有条件
- **关联条件** — JOIN 的 ON 条件
- **排序/限制** — ORDER BY、ROWNUM 限制
- **聚合条件** — GROUP BY、HAVING 条件

### 3.3 映射验证/校验点

识别所有验证逻辑：

- **IF 条件** — 每个 IF 及其分支的条件表达式
  ```sql
  IF NVL(V_QTY, 0) <= 0 THEN              ← 验证点：数量必须 > 0
  IF NVL(AD.PICKTOTRACEID, '*') != '*' THEN  ← 验证点：跟踪号不能已存在
  ```
- **RAISE 语句** — 错误的触发条件和错误消息内容
- **RETURN 语句** — 提前返回的条件和返回码
- **EXCEPTION 块** — 哪些异常被捕获，处理方式

## Step 4：连接数据库查询真实数据

### 4.1 连接数据库

使用 `connect-oracle` skill 连接数据库。连接字符串配置在项目根目录 `.env` 的 `DB_CONNECTION` 字段。

**⚠️ 重要**：
- 必须使用 Bash 工具（不可用 PowerShell）
- 变量引用使用双引号：`"$DB_CONNECTION"`
- 每条 SQL 末尾加 `EXIT;`

### 4.2 数据真实性铁律

**成功路径的所有入参值，必须来自数据库真实查询结果。** 以下做法都是违规的：

| ❌ 违规做法 | ✅ 正确做法 |
|-----------|-----------|
| 根据命名规则构造一个「看起来存在」的 ID | 先查数据库确认 ID 存在，再使用 |
| 把已知值的格式改一下当新数据用 | 查询出实际存在的不同值 |
| 使用「SELECT 1 FROM DUAL」之类和业务无关的数据 | 查询业务表获取真实数据 |
| 从代码注释中抄一个 ID 直接使用 | 到数据库验证该 ID 确实存在 |

**唯一例外 1：错误路径** — 为触发某个验证条件，可以构造不会通过验证的值（如不存在的 ID、空值、错误状态等）。但即使如此，也应优先基于真实数据做修改，并在用例中标注「构造值」。

**唯一例外 2：纯格式定义的字符串** — 如果存储过程的入参是代码中明确定义格式的字符串（如条码格式 `DC2^...^...`、HTTP URL 格式等），且数据库中没有对应的业务表可查询这些值，则可以按代码定义的格式构造。但此类情况必须在用例中说明「按代码格式构造，非数据库查询」。对于能从数据库查到的关联数据（如 SKU、客户 ID、订单号），仍必须从数据库查询。

### 4.3 按验证点查询数据

对每个验证点，设计并执行对应的查询：

**成功路径查询** — 找到能通过该验证的数据：
```sql
SELECT COUNT(1) AS CNT, ... FROM ... WHERE ... AND ROWNUM <= 10;
```

**错误路径查询** — 找到能触发该验证的条件：
```sql
-- 验证 "数量必须 > 0"
SELECT COUNT(1) AS CNT FROM ... WHERE NVL(QTY_EACH, 0) <= 0 AND ROWNUM <= 10;

-- 验证 "库位不能已被占用"
SELECT COUNT(1) AS CNT FROM ... WHERE NVL(TRACEID, '*') != '*' AND ROWNUM <= 10;
```

### 4.4 在查询中逐步递进

当不确定数据是否存在时，从最宽松到最严格的顺序查询：

```
① 查总数 → ② 减条件查 → ③ 加条件缩小 → ④ 找到精确匹配
```

记录每一步的结果，这样即使最终找不到完全匹配的数据，也能给出部分可用的测试数据。

### 4.5 查询环境约束

执行查询时必须始终附带业务约束条件（如本项目的多组织/多仓库）：

```sql
WHERE ORGANIZATIONID = 'DONGCHENG' AND WAREHOUSEID = 'DCCP'
```

如果不知道特定的约束值，先查询可用的组织/仓库：
```sql
SELECT DISTINCT ORGANIZATIONID, WAREHOUSEID FROM BAS_LOCATION WHERE ROWNUM <= 5;
```

### 4.6 数据记录要求

对每个查询结果，记录：
- **查询语句** — 完整的 SQL
- **返回数据** — 关键字段的值
- **数据量** — COUNT 值或行数
- **用途** — 这条数据用于哪个验证点的哪个路径

## Step 5：生成结构化测试方案

### 5.1 输出物规范

将测试方案保存到 `outputs/` 目录，命名格式：

```
[ProcedureName]_[YYYYMMDD]_TEST_PLAN.md
```

例如：
```
SPUDF_SWL_4FPICK_PROCESS_20260227_TEST_PLAN.md
```

### 5.2 测试方案结构

测试方案必须使用以下模板，言简意赅，**不需要包含**以下章节：「过程概述」「验证点矩阵」「内部验证点参考」「注意事项和限制」。

必须包含的章节：

``````markdown
# [过程名称] 测试方案

## 1. 依赖链
- 完整的调用树
- 关键参数传递关系

## 2. 数据准备
- 前置条件（需要在数据库中存在的状态）
- 依赖的基础数据
- **数据来源声明**（每个值来自哪次数据库查询）

## 3. 测试用例清单

### 3.1 成功路径（Happy Path）

| 用例编号 | 用例描述 | 入参 | 预期 OUT_CODE | 覆盖的验证点 |
|---------|---------|------|--------------|------------|
| HP-01   | ...     | ...  | 000#         | ...        |

### 3.2 错误路径（Error Path）

| 用例编号 | 用例描述 | 入参 | 预期 OUT_CODE | 覆盖的验证点 |
|---------|---------|------|--------------|------------|
| EP-01   | ...     | ...  | 999#...      | ...        |

## 4. 详细测试用例

### HP-01：[用例名称]
- **入参清单**：
  ```
  IN_PARAM1 => '实际值'
  IN_PARAM2 => '实际值'
  ```
- **预期结果**：`OUT_CODE = '000#'`
- **覆盖验证点**：验证点 A、验证点 B
- **验证 SQL**：
  ```sql
  -- 执行后检查状态的 SQL
  SELECT ... FROM ... WHERE ...;
  ```
- **前置条件**：
  - 需要在数据库中存在 X 数据

### EP-01：[用例名称]
- ...（同上结构）

## 5. 测试数据来源
- 记录每个查询的完整 SQL 和返回数据
- 记录数据所属的组织/仓库
- **标记每个入参值对应的查询来源**（证明数据真实性）
- 对于错误样本中编造的值，**显式标注「构造值」**并说明原因
``````

### 5.3 测试用例设计原则

**成功路径**：
- 至少产出 2 个不同的成功路径测试用例（如果存储过程是单一操作类型导致确实无法产出多个 HP，至少确保 1 个完整可用的 HP）
- 覆盖主流程的每个步骤都能通过
- 测试边界条件（如最少数量的数据）
- 测试典型业务场景
- **每个入参值都必须有数据库查询结果作为依据**（纯代码定义格式的字符串除外）

**错误路径**：
- 每个验证点至少有一个触发用例
- 每个 RAISE 语句至少有一个触发用例
- 每个 EXCEPTION 块（NO_DATA_FOUND, TOO_MANY_ROWS）至少有一个触发用例
- 测试空值、不存在、重复、状态不匹配等场景
- 错误样本可以编造数据，但**必须在用例中标注「构造值」**

### 5.4 验证 SQL

为每个测试用例提供可用于验证结果的 SQL 示例：

- **执行前验证** — 验证前置条件已满足
- **执行后验证** — 验证数据状态已按预期变化
- **状态查询** — 查询关键表的状态字段

执行完成后，逐项检查。**标 ★ 的为必须通过项，不通过则任务失败：**

- [★] **只读原则**：全程没有执行任何 INSERT / UPDATE / DELETE / CREATE / ALTER / DROP？
- [★] **数据真实**：所有成功路径的入参值都来自数据库真实查询，没有编造？
- [★] **业务约束**：每条查询都使用了正确的 ORGANIZATIONID 和 WAREHOUSEID？
- [ ] 是否读取了主过程完整源码？
- [ ] 是否递归追踪了所有子过程？
- [ ] 是否记录了每个过程的参数签名？
- [ ] 是否识别了所有验证点（IF/RAISE/RETURN）？
- [ ] 是否对每个验证点设计了成功和失败用例？
- [ ] 是否同时包含了成功和错误路径？
- [ ] 每个 RAISE/RETURN 是否都有对应的错误用例？
- [ ] 错误样本中的构造值是否已显式标注？
- [ ] 测试方案是否保存到 `outputs/` 目录？

## 常见陷阱

| 陷阱 | 说明 | 避免方法 |
|------|------|---------|
| 忽略子过程 | 子过程中的验证点同样关键 | 递归追踪完整调用链 |
| 只测成功路径 | 错误路径才是 bug 高发区 | 每个验证点都要有错误用例 |
| **编造数据** | **最常见的违规行为** | **成功路径数据必须从数据库查出来** |
| 忘记业务约束 | 查到其他组织的数据导致无效 | 每条查询都附带 ORGANIZATIONID |
| 参数值不带上下文 | 只看参数值不理解业务含义 | 每个参数值说明其业务含义 |
| 忽略 NULL 情况 | Oracle 中 NULL 语义特殊 | 特意设计 NULL/空值的测试用例 |
| 使用 12c+ 语法 | Oracle 11g 不支持 FETCH FIRST 等 | 使用 ROWNUM <= N |

## 与 sp-test skill 的关系

- **sp-test-data-gen**（本 skill）：生成测试方案。负责分析代码、查询数据、设计测试用例、输出测试文档。
- **sp-test**：执行测试方案。负责读取测试文档、构建测试脚本、连接到数据库执行、验证结果。

工作流程为：先用本 skill 生成测试方案，再用 sp-test 执行。
